fix(qualifying): resolve three post-implementation issues from
performance diagnostic

Following the main Qualifying page performance implementation
(analysis consolidation, visibility deferral, staleTime Infinity),
a post-implementation diagnostic identified three issues that
needed to be addressed. This commit resolves all three.

---

Fix 1: Move the scroll-trigger to the correct position on the page

Background:
The previous performance implementation added a feature that
defers the heavy analysis request until the user scrolls down
to the analysis section. The idea is that most users come to
the Qualifying page to look at the telemetry chart and sector
breakdown at the top — if they never scroll to the analysis
panels below, there is no reason to run a 6-7 second computation
on their behalf. The analysis request should only start when the
user is actually approaching that section.

The problem:
The scroll detection point was attached to the wrong element.
It was positioned at approximately 779 pixels from the top of
the page — which happens to be within the visible area of most
desktop screens (typically 900-1440 pixels tall). Because the
detection point was already on screen when the page loaded, the
deferred analysis request was firing immediately on every desktop
load, making the deferral completely ineffective for the majority
of users. The fix only worked as intended on small screens and
mobile devices.

What was changed:
The scroll detection point was moved from the Delta chart panel
(~779px from top) to the Scaled Delta Analysis panel (~1350px
from top). This position is genuinely below the visible area on
all standard desktop displays, meaning the analysis request now
correctly waits until the user scrolls into the below-fold
section before firing. A single attribute was moved from one
HTML element to another — no logic, hooks, or conditions were
changed, only the placement of the trigger point.

Impact:
Desktop users who load the Qualifying page to view the telemetry
chart and sector breakdown no longer trigger the 6-7 second
analysis request at all. The deferral now works as intended
across all viewport sizes.

---

Fix 2: Remove unused code left behind by the consolidation

Background:
The main performance implementation consolidated three separate
analysis service calls into one. Before that work, the page used
a dedicated hook called useDeltaQuery to fetch delta analysis
data on its own. When the consolidation was implemented, delta
data was folded into the single unified analysis response, making
the standalone useDeltaQuery hook redundant.

The problem:
The useDeltaQuery hook file and its export were not removed as
part of the consolidation. The hook continued to exist in the
codebase — with a cache setting of 30 seconds, inconsistent with
the Infinity policy applied to all active qualifying hooks — even
though no component in the application was using it. Unused code
that is still exported and visible creates unnecessary confusion
about what the codebase actually uses.

What was changed:
The useDeltaQuery.ts file was deleted and its corresponding
export was removed from the hooks barrel file. A full search
across the codebase confirmed zero remaining references before
deletion. TypeScript compilation confirmed no component depended
on it.

Impact:
The codebase accurately reflects what is actually in use. No
component, page, or feature is affected — the hook was genuinely
dead code.

---

Fix 3: Protect each panel from isolated failures

Background:
When a software component encounters an unexpected error — such
as a network failure, an unexpected data format, or a null value
where a value was expected — it can crash not just itself but
everything around it. Without a protective wrapper, a single
failing panel on the Qualifying page would cause the entire page
to go blank, showing nothing to the user even though the other
five panels loaded successfully.

The Race page already solved this problem using a pattern called
an ErrorBoundary — a wrapper that catches failures in the
component it contains and shows a controlled fallback message
instead of crashing the whole page. The Qualifying page was
missing this protection, which was identified as a pre-existing
gap in the diagnostic.

What was changed:
All six qualifying panels (Telemetry, Sectors, Delta, Scaled
Delta Analysis, Corner Analysis, and Performance Insights) were
wrapped in ErrorBoundary components using the exact same pattern
and import path used by the Race page. Each boundary also
includes a session identifier key so that when the user switches
to a different Grand Prix, any error state from the previous
round is automatically cleared and the panel attempts to load
fresh data for the new selection.

Impact:
A failure in any one panel now shows a contained amber warning
message ("Something went wrong rendering this panel") without
affecting the other five panels. The page remains functional and
informative even in partial failure scenarios. This matches the
resilience behaviour already in place on the Race page.
